# v0.1.0-rc1 independent-audit remediation

Every finding below was reproduced against public `v0.1.0-rc1` before anything was
changed. None of them was already fixed on the private successor branch.

Reproduction commands assume a clean clone of the tag:

```bash
git clone https://github.com/yusufdxb/ivf.git && cd ivf
git checkout v0.1.0-rc1
env -u PYTHONPATH uv sync --frozen
```

---

## H1 — Corrected case provenance

**Original severity:** high. **Reproduced:** yes.

```bash
sha256sum artifacts/cartpole-physx-baseline/trajectories.npz \
          artifacts/cartpole-physx-corrected/trajectories.npz
diff <(python3 -m json.tool artifacts/cartpole-physx-baseline/metadata.json) \
     <(python3 -m json.tool artifacts/cartpole-physx-corrected/metadata.json)
diff validation/capture/cartpole_physx.yaml validation/capture/cartpole_physx_corrected.yaml
```

Observed:

* both payloads are `62484fdd9a6b2386bcfa63265514686afc8b6ffa1e99b1d71b1225850b8783ed`;
* the two metadata files differ only in `capture_spec.name`;
* the two **capture specs** differ only in `name`, so there was no defect to remove.

The shipped manifest described the candidate as "a fresh capture from the same simulator
with the defect removed" and as "the negative control for the whole comparison", and that
text is sealed inside the evidence bundle's `verdict.json`.

**Impact:** the primary negative control exercised no tolerance, because a zero difference
cannot. A reader who believed the description would have concluded the tolerances had been
demonstrated to admit real variation. They had not.

**Independent execution.** Two further captures were run as separate processes, each
booting Kit independently, from the capture environment recorded in the bundles:

```bash
parity-capture validation/capture/cartpole_physx_corrected.yaml --output <dir-A>
parity-capture validation/capture/cartpole_physx.yaml          --output <dir-B>
```

Both produced payload `62484fdd…`, byte-identical to the shipped baseline. A freshly
written bundle differs from the shipped one only in the `hardware.gpu` string, which
sanitization coarsened.

**Correction.**

* PhysX on the recorded machine is bit-deterministic across independent runs, so the
  shipped artifact is *consistent with* independent deterministic re-execution. It is also
  *indistinguishable from a copy*, because `trajectory_bundle/v1` recorded nothing that
  differs between the two. That is the schema gap, and it is what H2/M3 close.
* The case is relabelled as a **declared A/A identity check** and an **independent
  no-defect repeatability check**, with both what it establishes and what it does not
  written into the manifest description.
* The **benign-difference case** is now the primary engineering negative control: it
  carries a real configuration change and a real nonzero accepted divergence
  (1.450e-3 rad, 4.199e-3 rad/s).

The exact public wording is:

> Independent deterministic re-execution produced identical scientific arrays on the
> recorded machine.

This is not presented as evidence of tolerance to capture variation.

**Remaining limitation:** determinism was observed on one machine, in one environment, for
one workload. Nothing here supports a cross-machine determinism claim, and none is made.

**Additional finding.** The same defect exists in the synthetic case study:
`validation/examples/synthetic_fixed.yaml` declared identical subject parameters while
describing itself as "the negative control for the whole validator". It is relabelled the
same way.

## H2 — Unit and per-array frame enforcement

**Original severity:** high. **Reproduced:** yes, and more severely than described.

Take a legitimately finalized bundle that declares `pole_angle` in degrees:

```bash
python - <<'PY'
import json, shutil, pathlib, sys
sys.path.insert(0, "src")
from ivf.bundle import finalize_v1
dst = pathlib.Path("/tmp/deg"); shutil.rmtree(dst, ignore_errors=True)
shutil.copytree("artifacts/cartpole-physx-corrected", dst)
(dst/"COMPLETE").unlink(); (dst/"CHECKSUMS.sha256").unlink()
m = json.loads((dst/"metadata.json").read_text())
m["capture_contract"]["arrays"]["pole_angle"]["unit"] = "deg"
(dst/"metadata.json").write_text(json.dumps(m, indent=2, sort_keys=True)+"\n")
finalize_v1(dst, run_status="completed")
PY
sed 's|artifacts/cartpole-physx-corrected|/tmp/deg|' \
  validation/examples/cartpole_corrected.yaml > /tmp/m.yaml
uv run ivf validate /tmp/m.yaml
```

Observed on RC1: `PASS`, exit `0`, and the report printed

```
pole_angle_agreement: pole_angle: worst second_largest absolute error 0.000e+00 rad <= 2.880e-02 rad
```

that is, the **baseline's** unit label attached to a comparison against a candidate
declaring degrees. The frame mutation behaved identically.

**Impact:** the declarations `trajectory_bundle/v1` exists to carry were recorded and never
compared. A unit or frame error, the exact class of defect a migration harness is for,
passed silently with a confident number.

**Correction.** `src/ivf/signal_contract.py` verifies, for every signal an oracle actually
consumes and without any manifest opt-in: unit, frame, dtype, and the compatibility of each
tolerance's unit with the signal it gates. Mixed-unit arrays such as `joint_pos`
(`"rad and m"`) are refused outright when an oracle would reduce them to one scalar against
one threshold. Missing declarations are `unverifiable`, never "matched". An invalidated
experiment now runs **no oracles at all**.

Reason codes: `IVF-CONTROL-SIGNAL-UNIT-MISMATCH`, `IVF-CONTROL-SIGNAL-FRAME-MISMATCH`,
`IVF-CONTROL-SIGNAL-DTYPE-MISMATCH`, `IVF-CONTROL-TOLERANCE-UNIT-MISMATCH`,
`IVF-CONTROL-MIXED-UNIT-REDUCTION-INVALID`.

**Tests:** `tests/test_signal_contract.py`, twelve cases including the matching-contract
case, so a validator that refuses everything fails as hard as one that refuses nothing.

**Remaining limitation:** units are compared as declared strings after normalizing case and
stripping parentheticals. There is no dimensional algebra, so `m` and `cm` are refused as
different rather than converted, and a capture that declares a unit wrongly but
*consistently* on both sides is still not detectable from the data.

## M1 — Seal threat model

**Original severity:** medium. **Reproduced:** yes.

RC1 described bundles as "tamper-evident". A coordinated edit plus reseal verifies as
internally consistent, because the seal is an unkeyed digest over content the editor
controls.

**Correction.** Consistent wording across README, evidence schema, claims table, CLI help,
`ivf reproduce` output, and the rendered report:

> IVF evidence bundles include checksums and an integrity seal that detect accidental
> corruption, incomplete transfer, and uncoordinated modification. The seal is not a digital
> signature and does not establish authenticity against an actor who can modify and reseal
> the entire bundle.

The CLI now prints `integrity verified against included seal`.

**Tests:** `tests/test_cli.py::test_the_seal_detects_uncoordinated_change_but_not_a_coordinated_reseal`
asserts all five behaviours, including the boundary itself.

**Remaining limitation:** by design. No signing infrastructure was added in this cycle.

## M2 — CLI operational errors

**Original severity:** medium. **Reproduced:** yes.

```bash
mkdir /tmp/notevidence
uv run ivf reproduce /tmp/notevidence --verify-only; echo "EXIT=$?"
```

Observed on RC1: a raw Python traceback and **exit 1**, the code reserved for a scientific
`FAIL`.

**Impact:** a CI job could not distinguish a typo from a regression.

**Correction.** `ivf.cli._operational_error` maps expected failures to `ERROR` with a stable
reason code and exit `5`: missing paths, unreadable or malformed evidence, checksum
mismatches, unknown evidence schemas, manifest errors, and ordinary `OSError`. Output is one
actionable line; `--debug` restores the traceback.

Verified after the fix:

```
ERROR
IVF-CLI-EVIDENCE-UNREADABLE
/tmp/notevidence: not an IVF evidence bundle (no verdict.json)
re-run with --debug for the traceback
EXIT=5
```

**Remaining limitation:** an unanticipated internal error maps to
`IVF-CLI-UNEXPECTED-ERROR` and exit 5. That is deliberate, but it means a genuine IVF bug
reports as an operational error rather than announcing itself.

## M3 — Input identity and self-comparison

**Original severity:** medium. **Reproduced:** yes.

`uv run ivf validate validation/examples/cartpole_corrected.yaml` returned `PASS` on two
subjects with identical content, with nothing in the output saying so.

**Correction.**

* Loading a strict bundle records its finalized checksum root, payload digest, capture id,
  creation time, and producer. These are written into `provenance.json` under
  `subject_identities`, so a sealed verdict names its own inputs.
* Identical subject content is refused by default with `IVF-EXPERIMENT-SELF-COMPARISON`,
  and no oracle runs.
* `experiment_mode: identity_check` declares an intentional A/A run. The report then states
  that it tests validator identity behaviour and does not establish independent
  repeatability or equivalence. Declaring identity mode while the subjects differ is itself
  refused.
* `trajectory_bundle/v1` gained an optional additive `capture` block
  (`capture_id`, `created_utc`, `independent_run`, `producer`, `execution` with
  host/user/paths redacted).

**Tests:** in `tests/test_signal_contract.py`, including the case that a copy carrying a
different `capture_id` is still detected as identical content. A declared id is not
evidence of a distinct run, because a copy can carry any id its author types.

**Remaining limitation:** content identity is computed over the arrays. Two independent runs
of a deterministic simulator are therefore indistinguishable from a copy *by construction*,
and no schema field can close that, which is why the corrected case is documented rather
than asserted.

## M6 — Release-equivalence claims

**Original severity:** medium. **Reproduced:** yes.

`docs/releases/v0.1.0-rc1-equivalence.json` published aggregate digests with no stated
algorithm, and object ids (`retained_original_producer_reference`, `original_producer_tree`,
`original_release_tree`, `rewritten_release_base`) naming private history that no reader can
resolve.

**Correction.**

* `tools/recompute_release_equivalence.py` recomputes all seven public aggregates with the
  selection, ordering, encoding, and concatenation format written down:

  ```bash
  git worktree add /tmp/rc1 v0.1.0-rc1
  python tools/recompute_release_equivalence.py --check --root /tmp/rc1
  ```

* The record is split into `publicly_recomputable` and `author_attested`, the latter saying
  plainly that its statements are not independently verifiable.
* Unresolvable object ids were removed from the record and from the reproduction guide.

**Tests:** `tests/test_release_equivalence.py`, including a check that no unresolvable
object id is published.

**Remaining limitation:** the private-history statements remain unverifiable by anyone but
the author. Labelling is the whole of the fix; it does not make them checkable.
